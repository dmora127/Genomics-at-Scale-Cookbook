This tutorial guides you through mapping long sequencing reads to a reference genome with Minimap2 on the CHTC high-throughput computing (HTC) system. You will learn how to:

* Index a reference genome once and reuse the index in every mapping job
* Split a large read file into chunks that can be mapped independently
* Map hundreds of chunks in parallel and sort the alignments with samtools
* Deliver the container image and the reference index to jobs with the Open Science Data Federation (OSDF)

The steps of this tutorial run across hundreds of jobs using the HTCondor workload manager and Apptainer containers to execute your software reliably and reproducibly at scale. The tutorial uses real long-read data from a California condor and emphasizes performance, reproducibility, and portability.

## Understanding Read Mapping

Read mapping, or alignment, finds the place in a reference genome that each sequencing read came from. It is the step that turns a pile of reads into something you can inspect position by position: coverage, variants, structural rearrangements, or methylation all start from mapped reads.

[Minimap2](https://github.com/lh3/minimap2) is the standard mapper for long reads. It handles reads tens of kilobases long, it is fast, and it ships presets that tune its parameters for each read type: `map-ont` for Oxford Nanopore reads, `map-hifi` for PacBio HiFi reads, `map-pb` for older PacBio reads, and `sr` for short reads. Minimap2 writes alignments in the text SAM format. The companion tool [samtools](https://www.htslib.org/) converts SAM to the compressed BAM format and sorts the alignments by position, which downstream tools such as variant callers and genome browsers require.

Before it can map anything, Minimap2 needs an index of the reference genome: a table of short, carefully chosen k-mers (minimizers) and their positions. Minimap2 can build the index on the fly, but for a genome of over a gigabase that takes minutes and several gigabytes of memory every time. Building the index once with `minimap2 -d` and saving it as a `.mmi` file lets every mapping job load it in seconds instead.

## Mapping by Read Chunk

Each read is mapped independently of every other read, so a FASTQ file can be cut at any read boundary and the pieces mapped in parallel. The results are identical to mapping the whole file at once; only the wall-clock time changes. This is the same principle that drives the [Dorado basecalling recipe](../01-Basecalling-GPUs/01.1-Introduction.md): many small, independent jobs working together to finish a large workload quickly.

In this tutorial you split about 261,000 condor reads into 262 chunks of 1,000 reads with the standard `split` command, and each chunk becomes one HTCondor job. The 262 jobs run wherever CHTC has free CPUs and finish in the time the slowest chunk takes, plus the wait in the queue.

Two files are needed by every one of those jobs: the container image and the reference index. Both are large, both are read-only, and both are identical for all jobs, so they live in your `/staging` directory and HTCondor fetches them through OSDF, which caches files close to the execute points. The read chunks are the opposite: small, used once, and different for every job, so they stay in your `/home` directory and HTCondor transfers each one directly. Deciding which files go where is the main data-management skill this recipe teaches.

Each job returns one sorted BAM file to `outputs/`. Merging those files into a single BAM is the first post-mapping step, covered in [Next Steps](./03.7-Next-Steps.md).
