With the index in `/staging` and the chunks listed in `listofReads.txt`, you are ready to map the reads as 262 independent jobs.

## Prepare Your Mapping Jobs: Executable and Submit File

### The Executable File: `minimap2_mapping.sh`

1. Change to your `genomics_tutorial/` directory:

   ```bash
   cd ~/genomics_tutorial/
   ```

2. Review the mapping executable `executables/minimap2_mapping.sh`. No changes are necessary:

   ```{code} bash
   :filename: executables/minimap2_mapping.sh
   :linenos:
   #!/bin/bash
   # Use minimap2 to map the basecalled reads to the reference genome
   minimap2 -ax map-ont "$1" "$2" > "mapped_${2}_reads_to_genome.sam"

   # Use samtools to sort our mapped reads BAM, required for downstream analysis
   samtools sort "mapped_${2}_reads_to_genome.sam" -o "mapped_${2}_reads_to_genome_sam_sorted.bam"
   ```

   The script takes two positional arguments:

   1. `$1`: the name of the reference index file (e.g. `G_californianus_813.fasta.mmi`).
   2. `$2`: the name of the read chunk (e.g. `subset_aa`).

   It maps the chunk with the `map-ont` preset, writing a SAM file, and then sorts the alignments by position into a compressed BAM file, `mapped_<chunk>_reads_to_genome_sam_sorted.bam`. The `-a` flag asks Minimap2 for full alignments in SAM format rather than the shorter PAF summary.

   :::{tip} Use the CPUs you request
   The submit file requests 2 CPUs, but the script as shipped runs Minimap2 and samtools on one thread. Add `-t 2` to the `minimap2` command and `-@ 2` to `samtools sort` to use both, and keep the numbers in step with `request_cpus` if you change it.
   :::

### The Submit File: `minimap2_mapping.sub`

3. Open `minimap2_mapping.sub` and fill in the placeholders. The cloned file has `<ref_genome_mmi_file_name>` in two places and `<NetID>` in two; replace them so that the file reads as follows:

   ```{code} bash
   :filename: minimap2_mapping.sub
   :linenos:
   :emphasize-lines: 1,4,6,19
   container_image        = osdf:///chtc/staging/<netid>/genomics_tutorial/software/minimap2_08OCT2025_v1.sif

   executable             = ./executables/minimap2_mapping.sh
   arguments              = G_californianus_813.fasta.mmi $(READ_SUBSET)

   transfer_input_files   = osdf:///chtc/staging/<netid>/genomics_tutorial/inputs/G_californianus_813.fasta.mmi, inputs/$(READ_SUBSET)

   transfer_output_files  = mapped_$(READ_SUBSET)_reads_to_genome_sam_sorted.bam
   transfer_output_remaps = "mapped_$(READ_SUBSET)_reads_to_genome_sam_sorted.bam = outputs/mapped_$(READ_SUBSET)_reads_to_genome_sam_sorted.bam"

   output                 = ./logs/$(Cluster)_$(Process)_mapping_$(READ_SUBSET)_step2.out
   error                  = ./logs/$(Cluster)_$(Process)_mapping_$(READ_SUBSET)_step2.err
   log                    = ./logs/$(Cluster)_mapping_step2.log

   request_cpus           = 2
   request_disk           = 5 GB
   request_memory         = 10 GB

   queue READ_SUBSET from listofReads.txt
   ```

   This submit file reads the contents of `listofReads.txt`, iterates through each line, and assigns the value of each line to the variable `$(READ_SUBSET)`. This lets you programmatically submit _N_ jobs, where _N_ equals the number of chunks you created. Each job transfers two input files: the reference index from your `/staging` directory through OSDF, and one read chunk from `inputs/` in your `/home` directory. The `container_image` attribute ensures your Minimap2 image is transferred and started for each job. For example:

   | Job | READ_SUBSET | Index                          | Machine                       |
   |-----|-------------|--------------------------------|-------------------------------|
   | 1   | subset_aa   | G_californianus_813.fasta.mmi  | slot1_1@e2345.chtc.wisc.edu   |
   | 2   | subset_ab   | G_californianus_813.fasta.mmi  | slot1_7@e4065.chtc.wisc.edu   |
   | ... | ...         | ...                            | ...                           |
   | 262 | subset_kb   | G_californianus_813.fasta.mmi  | slot1_3@e2345.chtc.wisc.edu   |

   The `transfer_output_files` line brings back only the sorted BAM. The SAM file is an intermediate that would double the output size, so it stays on the execute point and is deleted with the job's scratch directory. `transfer_output_remaps` places each BAM in `outputs/` instead of the submit directory. Its syntax is `"<file on the execute point> = <path on the Access Point>"`, with several remaps separated by semicolons.

   The submit file also specifies resource requests for each job: 2 CPUs, 5 GB of disk space, and 10 GB of memory. Most of the memory is the index, which Minimap2 loads in full.

   :::{hint} Using additional capacity outside of CHTC
   Because the container and the index travel by `osdf:///` URL and the chunks travel with the job, these jobs can run anywhere HTCondor can reach. Add `want_campus_pools = true` to let them run on other UW-Madison campus pools and `want_ospool = true` to let them run on the [OSPool](https://osg-htc.org/services/open_science_pool.html), a national pool of shared HTC capacity. Both increase the chance that your jobs start quickly. For details, see the CHTC guide [Scale Beyond Local HTC Capacity](https://chtc.cs.wisc.edu/uw-research-computing/scaling-htc).
   :::

## Submit and Monitor Your Mapping Jobs

4. Make sure the indexing job from [Index the Reference Genome](#minimap2-index-reference) has finished and the `.mmi` file is in `/staging/<netid>/genomics_tutorial/inputs/`.

5. Submit your mapping jobs:

   ```bash
   condor_submit minimap2_mapping.sub
   ```

   ```
   [<netid>@ap2001 genomics_tutorial]$ condor_submit minimap2_mapping.sub
   Submitting job(s)..........................................................................
   262 job(s) submitted to cluster 1234570.
   ```

6. Track your job progress:

   ```bash
   condor_watch_q
   ```

7. As jobs finish, their BAM files appear in `outputs/`:

   ```
   [<netid>@ap2001 genomics_tutorial]$ ls outputs/ | head -3
   mapped_subset_aa_reads_to_genome_sam_sorted.bam
   mapped_subset_ab_reads_to_genome_sam_sorted.bam
   mapped_subset_ac_reads_to_genome_sam_sorted.bam
   [<netid>@ap2001 genomics_tutorial]$ ls outputs/ | wc -l
   262
   ```

:::{tip} Held jobs
If you see held jobs, `condor_q -hold` shows the reason. A transfer error on the `.mmi` file usually means the indexing job had not finished, or the `<netid>` in the `osdf:///` URL is wrong; a memory overrun means the chunk needed more than 10 GB. Fix the cause, then use `condor_qedit` to change a resource request and `condor_release` to resume the jobs. For more details, see the HTCondor manual pages for [condor_q](https://htcondor.readthedocs.io/en/latest/man-pages/condor_q.html), [condor_qedit](https://htcondor.readthedocs.io/en/latest/man-pages/condor_qedit.html), and [condor_release](https://htcondor.readthedocs.io/en/latest/man-pages/condor_release.html), and the [CHTC guides](https://chtc.cs.wisc.edu/uw-research-computing/guides).
:::
