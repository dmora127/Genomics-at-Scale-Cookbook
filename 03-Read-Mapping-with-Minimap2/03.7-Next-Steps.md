## Post-Mapping Steps

You should now have 262 sorted BAM files in `outputs/`, one per read chunk. Almost every downstream tool wants a single BAM with an index, so the first post-mapping step is to merge them. Merging 262 files of this size takes a few minutes and a few gigabytes of memory, so run it as one more job rather than on the Access Point. Save the following two files and submit the job with `condor_submit merge_bams.sub`:

```{code} bash
:filename: executables/merge_bams.sh
:linenos:
#!/bin/bash
# Merge the per-chunk sorted BAMs into one sorted BAM and index it
samtools merge -@ 4 -o condor_mapped_sorted.bam mapped_subset_*_reads_to_genome_sam_sorted.bam
samtools index condor_mapped_sorted.bam
```

```{code} bash
:filename: merge_bams.sub
:linenos:
container_image        = osdf:///chtc/staging/<netid>/genomics_tutorial/software/minimap2_08OCT2025_v1.sif

executable             = ./executables/merge_bams.sh

transfer_input_files   = outputs/
transfer_output_files  = condor_mapped_sorted.bam, condor_mapped_sorted.bam.bai
transfer_output_remaps = "condor_mapped_sorted.bam = outputs/condor_mapped_sorted.bam; \
                          condor_mapped_sorted.bam.bai = outputs/condor_mapped_sorted.bam.bai"

output                 = ./logs/$(Cluster)_merge_step3.out
error                  = ./logs/$(Cluster)_merge_step3.err
log                    = ./logs/$(Cluster)_merge_step3.log

request_cpus           = 4
request_disk           = 20 GB
request_memory         = 8 GB

queue 1
```

The trailing slash in `transfer_input_files = outputs/` transfers the contents of the directory, so the per-chunk BAMs land in the top level of the job's scratch directory where the `mapped_subset_*` pattern finds them. Once the merged BAM is back in `outputs/`, `samtools flagstat outputs/condor_mapped_sorted.bam` reports how many reads mapped, and the BAM and its `.bai` index can be loaded into a genome browser such as [IGV](https://igv.org/).

## Next Steps

Now that you have completed this read mapping tutorial on CHTC, you are ready to adapt the workflow to your own data and research questions. Here are some suggestions for what to do next.

### Apply the Workflow to Your Own Data

* Replace the tutorial reads and reference genome with your own files. Index your reference once, split your reads, and regenerate `listofReads.txt`.
* Modify the mapping submit file to fit your data size, read type (e.g. `map-ont` vs. `map-hifi`), and resource needs. Larger chunks need more disk; a larger genome needs more memory for the index.

### Customize or Extend the Workflow

* Run [FastQC](../02-Quality-with-FASTQC/02.1-Introduction.md) on your reads before mapping, or feed basecalled reads from the [Dorado recipe](../01-Basecalling-GPUs/01.1-Introduction.md) into this one.
* Call structural variants on the merged BAM with [Sniffles2](https://github.com/fritzsedlazeck/Sniffles). The repository ships `software/sniffles2.def`; build it the same way as the Minimap2 container.
* Use other mappers or variant callers, such as NGMLR, pbsv, or cuteSV, by swapping the container and the executable.
* Add downstream tools for annotation, comparison, or visualization (e.g. IGV, bedtools, SURVIVOR).

### Create Your Own Containers

* Extend the Apptainer containers used here with additional tools, reference data, or dependencies.
* For help with this, see the [CHTC software guides](https://chtc.cs.wisc.edu/uw-research-computing/software-overview-htc).

### Run Larger Analyses

* Submit thousands of mapping jobs across CHTC. The index and the container are fetched through OSDF no matter how many jobs there are.
* Explore data staging best practices for large-scale genomics workflows, including OSDF.
* Chain indexing, splitting, mapping, and merging into one workflow with [DAGMan](https://chtc.cs.wisc.edu/uw-research-computing/dagman-workflows), so that the mapping jobs wait for the index automatically.

### Get Help or Collaborate

* Reach out to [chtc@cs.wisc.edu](mailto:chtc@cs.wisc.edu) for one-on-one help with scaling your research.
* Attend office hours or training sessions. See the [CHTC Get Help page](https://chtc.cs.wisc.edu/uw-research-computing/get-help.html) for details.

## Software

In this tutorial you used a *starter* Apptainer container with Minimap2, samtools, and bedtools, and the repository ships a second recipe for Sniffles2. These containers can serve as a jumping-off point if you need to install additional software for your workflows.

Our recommendation for most users is to use Apptainer containers for deploying their software. For instructions on how to build an Apptainer container, see the guide [Using Apptainer/Singularity Containers](https://chtc.cs.wisc.edu/uw-research-computing/apptainer-htc). If you are familiar with Docker, or want to learn how to use Docker, see the guide [Using Docker Containers](https://chtc.cs.wisc.edu/uw-research-computing/docker-jobs).

This information can also be found in the guide [Using Software on CHTC](https://chtc.cs.wisc.edu/uw-research-computing/software-overview-htc).

## Data

The ecosystem for moving data to, from, and within the HTC system can be complex, especially when working with large data (many gigabytes). This recipe used three of its mechanisms: direct transfer from `/home` for the read chunks, `osdf:///` URLs for the container and the index in `/staging`, and `transfer_output_remaps` to write the index straight back to `/staging`. For guides on how data movement works on the HTC system, see the [Data Staging and Transfer to Jobs](https://chtc.cs.wisc.edu/uw-research-computing/htc-job-file-transfer) guides.
