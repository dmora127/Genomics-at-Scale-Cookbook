One job worked. Now run FastQC on all six files with a single submit file and a single `condor_submit` command. The only changes are a list of sample names and a variable that stands in for the sample name everywhere it appeared in `fastqc.submit`.

## Create a List of Samples

1. Change to your `tutorial-fastqc/` directory:

   ```bash
   cd ~/tutorial-fastqc/
   ```

2. Build the list of samples from the file names in `data/`. The `cut` command keeps everything before the first `.`, so `SRR2584863_1.trim.sub.fastq` becomes `SRR2584863_1`:

   ```bash
   ls data/ | cut -f1 -d "." > list_of_samples.txt
   ```

3. Check the list. Each line will become one job:

   ```
   [<netid>@ap2001 tutorial-fastqc]$ cat list_of_samples.txt
   SRR2584863_1
   SRR2584863_2
   SRR2584866_1
   SRR2584866_2
   SRR2589044_1
   SRR2589044_2
   ```

## The Submit File: `many-fastqc.submit`

4. Review `many-fastqc.submit`. It is `fastqc.submit` with every occurrence of the sample name replaced by the variable `$(sample)`, and with a `queue` statement that reads sample names from the list. No changes are necessary:

   ```{code} bash
   :filename: many-fastqc.submit
   :linenos:
   :emphasize-lines: 5,12,16-17,20-22,30
   # HTCondor Submit File: many-fastqc.submit

   # Provide our executable and arguments
   executable = fastqc.sh
   arguments = $(sample).trim.sub.fastq

   # Provide the container for our software
   universe    = container
   container_image = software/fastqc.sif

   # List files that need to be transferred to the job
   transfer_input_files = data/$(sample).trim.sub.fastq
   should_transfer_files = YES

   # Tell HTCondor to transfer output to our /results directory
   transfer_output_files = $(sample).trim.sub_fastqc.html
   transfer_output_remaps = "$(sample).trim.sub_fastqc.html = results/$(sample).trim.sub_fastqc.html"

   # Track job information
   log = logs/$(sample).fastqc.log
   output = logs/$(sample).fastqc.out
   error = logs/$(sample).fastqc.err

   # Resource Requests
   request_cpus = 1
   request_memory = 1GB
   request_disk = 1GB

   # Tell HTCondor to run our job once:
   queue sample from list_of_samples.txt
   ```

   The `queue sample from list_of_samples.txt` statement reads the list one line at a time, sets `$(sample)` to the value on that line, and creates one job. HTCondor substitutes the value wherever `$(sample)` appears, so each job transfers its own input file, returns its own report, and writes its own log files. Giving the logs per-sample names matters: six jobs writing to one `fastqc.out` would overwrite each other.

   | Job | sample | Input file | Report |
   |-----|--------|------------|--------|
   | 1 | SRR2584863_1 | data/SRR2584863_1.trim.sub.fastq | results/SRR2584863_1.trim.sub_fastqc.html |
   | 2 | SRR2584863_2 | data/SRR2584863_2.trim.sub.fastq | results/SRR2584863_2.trim.sub_fastqc.html |
   | 3 | SRR2584866_1 | data/SRR2584866_1.trim.sub.fastq | results/SRR2584866_1.trim.sub_fastqc.html |
   | 4 | SRR2584866_2 | data/SRR2584866_2.trim.sub.fastq | results/SRR2584866_2.trim.sub_fastqc.html |
   | 5 | SRR2589044_1 | data/SRR2589044_1.trim.sub.fastq | results/SRR2589044_1.trim.sub_fastqc.html |
   | 6 | SRR2589044_2 | data/SRR2589044_2.trim.sub.fastq | results/SRR2589044_2.trim.sub_fastqc.html |

   :::{note} Other ways to queue many jobs
   `queue <variable> from <file>` is the form used throughout this cookbook because the list doubles as a record of what was run. HTCondor also offers `queue <variable> matching <pattern>` to build the list from file names directly and `queue <variable> in (<value> <value> ...)` for short lists. See [Submitting many similar jobs with one queue command](https://htcondor.readthedocs.io/en/latest/users-manual/submitting-a-job.html#submitting-many-similar-jobs-with-one-queue-command) in the HTCondor manual.
   :::

## Submit and Monitor Your Jobs

5. Submit all six jobs with one command:

   ```bash
   condor_submit many-fastqc.submit
   ```

   ```
   [<netid>@ap2001 tutorial-fastqc]$ condor_submit many-fastqc.submit
   Submitting job(s)......
   6 job(s) submitted to cluster 1234568.
   ```

   Notice that a **single submit file** put **six jobs** in the queue. They share a cluster ID and are numbered `1234568.0` through `1234568.5`.

6. Track their progress:

   ```bash
   condor_watch_q
   ```

7. When the jobs have finished, `results/` holds one report per file and `logs/` holds one set of log files per sample:

   ```
   [<netid>@ap2001 tutorial-fastqc]$ ls results/
   SRR2584863_1.trim.sub_fastqc.html  SRR2584866_1.trim.sub_fastqc.html  SRR2589044_1.trim.sub_fastqc.html
   SRR2584863_2.trim.sub_fastqc.html  SRR2584866_2.trim.sub_fastqc.html  SRR2589044_2.trim.sub_fastqc.html
   ```

:::{tip} Held jobs
If some jobs are held, `condor_q -hold` lists them with the reason. Fix the cause, then `condor_release` the jobs, or remove them with `condor_rm` and resubmit. Because each job is independent, the jobs that succeeded are unaffected.
:::

You have finished the first step of a sequencing analysis pipeline and, more importantly, you have turned one job into many without writing six submit files. The same `queue ... from` pattern drives the hundreds of jobs in the [Dorado basecalling](../01-Basecalling-GPUs/01.5-Basecall-Reads.md) and [Minimap2 mapping](../03-Read-Mapping-with-Minimap2/03.6-Map-Reads.md) recipes.
