This tutorial guides you through the first step of most sequencing analyses, read quality control, using FastQC on the CHTC high-throughput computing (HTC) system. You will learn how to:

* Run FastQC inside an Apptainer container that HTCondor sets up for you
* Write an executable and a submit file that process one FASTQ file
* Turn that single job into one job per sample with the `queue <variable> from <list>` syntax
* Collect the FastQC reports into a results directory with `transfer_output_remaps`

The pattern you practice here, one small independent job per input file, is the building block of every other recipe in this cookbook. FastQC is a convenient first example because each job needs a single file, a single CPU, and under a minute of run time, so you can concentrate on the HTCondor mechanics.

## Why Quality Control Comes First

Sequencing instruments make mistakes, and the mistakes are not random: quality often drops toward the end of a read, adapter sequence appears when a DNA fragment is shorter than the read length, and library preparation can leave duplicated or overrepresented sequences behind. If you skip quality control, these artifacts turn up later as false variants, fragmented assemblies, or mapping rates that are hard to explain.

[FastQC](https://www.bioinformatics.babraham.ac.uk/projects/fastqc/) reads a FASTQ file and writes an HTML report with a pass, warn, or fail flag for each of about a dozen checks, including:

* **Per-base sequence quality**: the distribution of quality scores at each position along the reads
* **Per-sequence quality scores**: how many reads have a low average quality
* **Adapter content**: how much of each read is adapter rather than insert
* **Sequence duplication levels** and **overrepresented sequences**: signs of PCR duplication or contamination
* **Per-base sequence content** and **GC content**: biases that hint at library preparation problems

The report tells you whether to trim reads, remove adapters, or drop a sample before you spend hours of compute on mapping or assembly.

## One Job per Sample

FastQC analyzes each file on its own: the report for one sample does not depend on any other sample. That makes read quality control an ideal high-throughput computing workload. Instead of running FastQC on your files one after another on a single machine, you submit one HTCondor job per file and let CHTC run them all at once. Six files finish in the time it takes to run one, and so do six hundred.

The tutorial builds this up in two steps. First you write a submit file that runs FastQC on one named file, submit it, and check the result. Then you replace the file name with a variable, point HTCondor at a list of samples, and submit the whole set with the same command.
