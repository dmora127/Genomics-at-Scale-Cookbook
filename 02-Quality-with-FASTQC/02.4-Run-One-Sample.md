With the reads in `data/` and the container in `software/`, you can assemble your first job. A job needs two files: an executable that HTCondor runs on the execute point, and a submit file that tells HTCondor what to transfer, what to run, and what resources to reserve.

## Prepare Your Job: Executable and Submit File

### The Executable File: `fastqc.sh`

1. Change to your `tutorial-fastqc/` directory:

   ```bash
   cd ~/tutorial-fastqc/
   ```

2. Review the executable `fastqc.sh`. No changes are necessary:

   ```{code} bash
   :filename: fastqc.sh
   :linenos:
   #!/bin/bash
   # Executable name: fastqc.sh

   # Run FastQC to determine the quality of our raw .fastq sequencing data
   fastqc $1
   ```

   The script takes one positional argument, the name of a FASTQ file, and runs `fastqc` on it. Because the job runs inside the FastQC container, the `fastqc` command is already on the `PATH`. FastQC writes two files next to the input: `<name>_fastqc.html`, the report, and `<name>_fastqc.zip`, an archive with the numbers and plots behind the report.

### The Submit File: `fastqc.submit`

3. Review the submit file `fastqc.submit`, which runs FastQC on the forward reads of the first sample. No changes are necessary:

   ```{code} bash
   :filename: fastqc.submit
   :linenos:
   :emphasize-lines: 5,9,12,16-17
   # HTCondor Submit File: fastqc.submit

   # Provide our executable and arguments
   executable = fastqc.sh
   arguments = SRR2584863_1.trim.sub.fastq

   # Provide the container for our software
   universe    = container
   container_image = software/fastqc.sif

   # List files that need to be transferred to the job
   transfer_input_files = data/SRR2584863_1.trim.sub.fastq
   should_transfer_files = YES

   # Tell HTCondor to transfer output to our /results directory
   transfer_output_files = SRR2584863_1.trim.sub_fastqc.html
   transfer_output_remaps = "SRR2584863_1.trim.sub_fastqc.html = results/SRR2584863_1.trim.sub_fastqc.html"

   # Track job information
   log = logs/fastqc.log
   output = logs/fastqc.out
   error = logs/fastqc.err

   # Resource Requests
   request_cpus = 1
   request_memory = 1GB
   request_disk = 1GB

   # Tell HTCondor to run our job once:
   queue 1
   ```

   The submit file tells HTCondor to:

   * Run `fastqc.sh` with the file name `SRR2584863_1.trim.sub.fastq` as its argument (`executable`, `arguments`).
   * Start the job inside `software/fastqc.sif` (`universe = container`, `container_image`). HTCondor transfers the image to the execute point together with the input files.
   * Copy `data/SRR2584863_1.trim.sub.fastq` into the job's scratch directory before the job starts (`transfer_input_files`). The executable sees the file by its bare name, which is why `arguments` has no `data/` prefix.
   * Bring back only the HTML report, and place it in `results/` instead of the directory you submitted from (`transfer_output_files`, `transfer_output_remaps`).
   * Write the HTCondor event log, the job's standard output, and its standard error to `logs/`.
   * Reserve 1 CPU, 1 GB of memory, and 1 GB of disk, which is plenty for a file of this size.

   :::{tip} Want the numbers behind the report?
   FastQC also writes `SRR2584863_1.trim.sub_fastqc.zip`, which contains `fastqc_data.txt` with every metric in plain text. Tools such as MultiQC read that file rather than the HTML. To keep it, list the zip file in both `transfer_output_files` and `transfer_output_remaps`:

   ```{code} bash
   :filename: fastqc.submit
   :lineno-start: 16
   transfer_output_files = SRR2584863_1.trim.sub_fastqc.html, SRR2584863_1.trim.sub_fastqc.zip
   transfer_output_remaps = "SRR2584863_1.trim.sub_fastqc.html = results/SRR2584863_1.trim.sub_fastqc.html; \
                             SRR2584863_1.trim.sub_fastqc.zip = results/SRR2584863_1.trim.sub_fastqc.zip"
   ```
   :::

## Submit and Monitor Your Job

4. Submit the job:

   ```bash
   condor_submit fastqc.submit
   ```

   HTCondor confirms the submission and reports the cluster ID:

   ```
   [<netid>@ap2001 tutorial-fastqc]$ condor_submit fastqc.submit
   Submitting job(s).
   1 job(s) submitted to cluster 1234567.
   ```

5. Track your job's progress. `condor_watch_q` updates in place until the job finishes; press `Ctrl+C` to leave it:

   ```bash
   condor_watch_q
   ```

   You can also take a one-time snapshot of the queue with `condor_q`.

6. Once the job has left the queue, look at the result that `transfer_output_remaps` placed in `results/`:

   ```
   [<netid>@ap2001 tutorial-fastqc]$ ls results/
   SRR2584863_1.trim.sub_fastqc.html
   ```

7. It is good practice to check the standard error, standard output, and HTCondor log files for anything unexpected, even when a job succeeds:

   ```
   [<netid>@ap2001 tutorial-fastqc]$ ls logs/
   fastqc.err  fastqc.log  fastqc.out
   ```

   `fastqc.out` holds FastQC's progress messages (`Started analysis of ...`, `Approx 5% complete ...`). `fastqc.err` is usually empty, and `fastqc.log` records when HTCondor submitted, started, and finished the job and how much memory and disk it used.

## View the Report

8. The report is an HTML file, so copy it to your own computer and open it in a browser. Run this on your laptop, not on the Access Point:

   ```bash
   scp <netid>@ap2001.chtc.wisc.edu:~/tutorial-fastqc/results/SRR2584863_1.trim.sub_fastqc.html .
   ```

   The left-hand column of the report lists each check with a green, orange, or red icon. The toy reads were already trimmed by Data Carpentry, so most checks pass.

:::{tip} Held jobs
If the job goes on hold, `condor_q -hold` shows the reason. Typical causes are a missing input file (check the `transfer_input_files` path) or a resource overrun. Fix the problem, then use `condor_release` to resume the job, or `condor_rm` it and resubmit. For more details, see the HTCondor manual pages for [condor_q](https://htcondor.readthedocs.io/en/latest/man-pages/condor_q.html) and [condor_release](https://htcondor.readthedocs.io/en/latest/man-pages/condor_release.html), and the [CHTC guides](https://chtc.cs.wisc.edu/uw-research-computing/guides).
:::
