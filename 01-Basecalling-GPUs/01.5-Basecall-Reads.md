Now that your data are organized into channel-specific subsets, you are ready to submit your basecalling jobs to CHTC.

## Prepare Your Basecalling Jobs: Executable and Submit File

### The Executable File: `run_dorado.sh`

1. Change to your `tutorial-ONT-Basecalling/` directory:

   ```bash
   cd ~/tutorial-ONT-Basecalling/
   ```

2. Review the Dorado basecalling executable `executables/run_dorado.sh`. No changes are necessary if you are using the script as shipped in the repository, reproduced below:

   ```{code} bash
   :filename: executables/run_dorado.sh
   :linenos:
   #!/bin/bash
   # Run Dorado on the EP for each POD5 file (non-resumeable)
   # Usage: ./run_dorado.sh "<dorado_args>" <dorado_model_name> <input_pod5_file>

   set -euo pipefail

   DORADO_ARGS="$1"
   DORADO_MODEL_NAME="$2"
   INPUT_POD5="$3"
   BAM_FILE="${INPUT_POD5}.bam"
   FASTQ_FILE="${BAM_FILE}.fastq"

   echo "Running Dorado with args: ${DORADO_ARGS}"
   echo "Model Name: ${DORADO_MODEL_NAME}"
   echo "Input POD5: ${INPUT_POD5}"
   echo "Output BAM: ${BAM_FILE}"

   # untar your Dorado basecalling models
   tar -xvzf ${DORADO_MODEL_NAME}.tar.gz
   rm ${DORADO_MODEL_NAME}.tar.gz
   echo "Completed model extraction."

   # Run Dorado
   dorado ${DORADO_ARGS} "${DORADO_MODEL_NAME}" "${INPUT_POD5}" > "${BAM_FILE}"
   echo "Completed Dorado basecalling."

   # Convert BAM to FASTQ
   bedtools bamtofastq -i "${BAM_FILE}" -fq "${FASTQ_FILE}"
   echo "Completed BAM → FASTQ conversion."
   ```

   This script accepts three positional arguments:

   1. `<dorado_args>`: the Dorado subcommand and options to run (e.g. `basecaller --device cuda:all --batchsize 16`).
   2. `<dorado_model_name>`: the name of the Dorado model tarball, without the `.tar.gz` extension (e.g. `dna_r10.4.1_e8.2_400bps_hac@v5.2.0`).
   3. `<input_pod5_file>`: the input POD5 file to be basecalled (e.g. `channel-100.pod5`).

   The script outputs two files: a BAM file (`<input_pod5_file>.bam`) and a FASTQ file (`<input_pod5_file>.bam.fastq`).

   The script runs a single Dorado basecalling job on the Execution Point (EP) for a given POD5 file. It first extracts the specified Dorado model from its tarball, then runs the Dorado basecaller with the provided arguments, the extracted model directory, and the input POD5 file, and finally converts the resulting BAM file to FASTQ format using `bedtools bamtofastq`.

### The Submit File: `run_dorado_at_CHTC.sub`

3. Open the submit file `~/tutorial-ONT-Basecalling/run_dorado_at_CHTC.sub` and replace the two `<netid>` placeholders in the `container_image` and `transfer_input_files` attributes with your NetID. If you downloaded a different Dorado model, update `DORADO_MODEL` to match. You may also edit the `arguments` attribute to change the Dorado basecalling parameters.

   ```{code} bash
   :filename: run_dorado_at_CHTC.sub
   :linenos:
   :emphasize-lines: 1,3,8,10
   container_image        = osdf:///chtc/staging/<netid>/tutorial-ONT-Basecalling/software/dorado_build1.2.0_27OCT2025_v1.sif

   DORADO_MODEL = dna_r10.4.1_e8.2_400bps_hac@v5.2.0

   executable             = ./executables/run_dorado.sh

   # First positional argument: the Dorado subcommand and options (the model and input file are appended by the script)
   arguments              = "'basecaller --device cuda:all --batchsize 16' $(DORADO_MODEL) $(POD5_input_file)"

   transfer_input_files   = inputs/split_pod5_subsets/$(POD5_input_file), osdf:///chtc/staging/<netid>/tutorial-ONT-Basecalling/data/$(DORADO_MODEL).tar.gz
   transfer_output_files  = $(POD5_input_file).bam, $(POD5_input_file).bam.fastq
   transfer_output_remaps = "$(POD5_input_file).bam = ./outputs/basecalledBAMs/$(POD5_input_file).bam; \
                             $(POD5_input_file).bam.fastq = ./outputs/basecalledFASTQs/$(POD5_input_file).bam.fastq"

   output                 = ./logs/out/$(POD5_input_file)_$(Process)_basecalling.out
   error                  = ./logs/err/$(POD5_input_file)_$(Process)_basecalling.err
   log                    = ./logs/$(POD5_input_file)_basecalling.log

   request_cpus           = 1
   request_disk           = 8 GB
   request_memory         = 4 GB
   retry_request_memory   = 24 GB
   request_gpus           = 1

   +WantGPULab            = true
   +GPUJobLength          = "short"

   queue POD5_input_file from list_of_pod5_files.txt
   ```

   :::{note} Which submit file?
   The repository contains two submit files. `run_dorado_at_CHTC.sub` (above) is for CHTC and transfers files from your `/staging` directory through OSDF. `run_dorado.sub` is the OSPool variant and is not used in this tutorial.
   :::

   :::{note} Passing the model to Dorado
   The `arguments` line passes the model as the name of the directory extracted from the model tarball, so Dorado uses exactly the model you downloaded in [Set Up Your Software Environment](#dorado-software-setup). If you pass a model *name* such as `hac@v5.2.0` instead, Dorado will try to resolve it and download the model at run time.
   :::

   This submit file reads the contents of `list_of_pod5_files.txt`, iterates through each line, and assigns the value of each line to the variable `$(POD5_input_file)`. This lets you programmatically submit _N_ jobs, where _N_ equals the number of POD5 subset files you created. Each job processes one POD5 channel subset (e.g. `channel-100.pod5`) using your Dorado model tarball (e.g. `dna_r10.4.1_e8.2_400bps_hac@v5.2.0.tar.gz`), both of which are transferred to the Execution Point (EP) by HTCondor. The `container_image` attribute ensures your `dorado_build1.2.0_27OCT2025_v1.sif` Apptainer image is transferred and started for each job. For example:

   | Job | POD5_input_file  | Dorado Model                       | Machine                       |
   |-----|------------------|------------------------------------|-------------------------------|
   | 1   | channel-100.pod5 | dna_r10.4.1_e8.2_400bps_hac@v5.2.0 | slot1_1@gpu2009.chtc.wisc.edu |
   | 2   | channel-101.pod5 | dna_r10.4.1_e8.2_400bps_hac@v5.2.0 | slot1_2@gpu2001.chtc.wisc.edu |
   | ... | ...              | ...                                | ...                           |
   | N   | channel-611.pod5 | dna_r10.4.1_e8.2_400bps_hac@v5.2.0 | slot1_3@gpu2009.chtc.wisc.edu |

   The submit file instructs the EP to run your executable `run_dorado.sh` and pass it the arguments found in the `arguments` attribute. The `arguments` attribute lets you customize the parameters passed to Dorado directly in your submit file, without editing your executable.

   The submit file also specifies resource requests for each job: 1 CPU, 1 GPU, 8 GB of disk space, and 4 GB of memory, with a retry at 24 GB if a job is held for exceeding its memory request. `+WantGPULab = true` and `+GPUJobLength = "short"` make the jobs eligible for the [CHTC GPU Lab](https://chtc.cs.wisc.edu/uw-research-computing/gpu-lab) and declare them short-running. Finally, the `transfer_output_remaps` attribute organizes the output files into specific directories within your tutorial folder.

   :::{hint} Using additional capacity outside of CHTC
   Dorado basecalling benefits from large pools of GPU resources. You can reach GPUs beyond the CHTC pool by adding the `want_campus_pools` and `want_ospool` attributes to your submit file. `want_campus_pools` lets your jobs run on other UW-Madison campus pools, and `want_ospool` lets them run on the [OSPool](https://osg-htc.org/services/open_science_pool.html), a national pool of shared HTC capacity that CHTC staff also operate. Both increase the chance that your jobs start quickly. Jobs that run outside CHTC cannot read `/staging` directly, which is why this tutorial transfers the container and model with `osdf:///` URLs. For details, see the CHTC guide [Scale Beyond Local HTC Capacity](https://chtc.cs.wisc.edu/uw-research-computing/scaling-htc).

   To enable this, add the following lines to your submit file:

   ```{code} bash
   :filename: run_dorado_at_CHTC.sub
   :linenos:
   :lineno-start: 26
   :emphasize-lines: 1-2
   want_campus_pools      = true
   want_ospool            = true

   queue POD5_input_file from list_of_pod5_files.txt
   ```
   :::

## Submit and Monitor Your Basecalling Jobs

4. Create the output and log directories that the submit file writes to:

   ```bash
   mkdir -p outputs/basecalledBAMs outputs/basecalledFASTQs logs/out logs/err
   ```

5. Submit your basecalling jobs:

   ```bash
   condor_submit run_dorado_at_CHTC.sub
   ```

6. Track your job progress:

   ```bash
   condor_watch_q
   ```

:::{tip} Held jobs
If you see held jobs (for example, for memory overruns), use `condor_qedit` to increase the resource request and `condor_release` to resume them. For more details, see the HTCondor manual pages for [condor_q](https://htcondor.readthedocs.io/en/latest/man-pages/condor_q.html), [condor_qedit](https://htcondor.readthedocs.io/en/latest/man-pages/condor_qedit.html), and [condor_release](https://htcondor.readthedocs.io/en/latest/man-pages/condor_release.html), and the [CHTC guides](https://chtc.cs.wisc.edu/uw-research-computing/guides).
:::
