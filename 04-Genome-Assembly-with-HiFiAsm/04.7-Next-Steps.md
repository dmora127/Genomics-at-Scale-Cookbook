## Next Steps

Now that you have assembled the Pallas's cat genome on CHTC, you are ready to adapt the workflow to your own data and research questions. Here are some suggestions for what to do next.

### Combine with Basecalling and Quality Control

* If you have raw Nanopore signal data, basecall it with the [Dorado recipe](../01-Basecalling-GPUs/01.1-Introduction.md) and feed the merged FASTQ into this recipe.
* Run [FastQC](../02-Quality-with-FASTQC/02.1-Introduction.md) or NanoPlot on the reads first. Read length and quality distributions explain a lot about assembly contiguity.

### Assess Assembly Quality

* Run [QUAST](https://quast.sourceforge.net/) to compute contiguity metrics (N50, total length, number of contigs).
* Run [BUSCO](https://busco.ezlab.org/) against the `mammalia_odb10` lineage database to assess gene completeness.
* Compare your metrics against published Felidae genomes.

### Use a Different Assembler

* Run Flye, Shasta, or Verkko on the same reads to compare results. Build a container for the tool the same way as in [Set Up Your Software Environment](#hifiasm-software-setup), and change only the command line in the executable.

### Scaffold, Polish, and Annotate

* Scaffold contigs into chromosome-level assemblies with Hi-C data and tools such as YaHS or SALSA2.
* Polish the assembly with additional sequencing data to reduce residual errors.
* Mask repeats (RepeatMasker, RepeatModeler) and predict genes (BRAKER, Augustus).

### Scale to Multiple Samples

* Adapt the workflow for multiple specimens with HTCondor's `queue ... from` syntax: a manifest file with one sample name and reads path per line, and `$(sample)` and `$(reads)` variables in `arguments` and `transfer_output_remaps`. The [FastQC recipe](../02-Quality-with-FASTQC/02.5-Scale-Out.md) shows the pattern.
* Chain quality control, assembly, and assessment into one workflow with [DAGMan](https://chtc.cs.wisc.edu/uw-research-computing/dagman-workflows).

### Get Help or Collaborate

* Reach out to [chtc@cs.wisc.edu](mailto:chtc@cs.wisc.edu) for one-on-one help with scaling your research.
* Attend office hours or training sessions. See the [CHTC Get Help page](https://chtc.cs.wisc.edu/uw-research-computing/get-help.html) for details.

## Glossary

| Term                                | Definition                                                                                                                          |
|-------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------|
| ONT (Oxford Nanopore Technologies)  | Long-read sequencing platform producing reads typically 10-100+ kb in length.                                                       |
| Ligation Sequencing                 | ONT library preparation method that ligates motor proteins to DNA fragments for sequencing.                                         |
| hifiasm                             | Fast haplotype-resolved de novo assembler supporting PacBio HiFi and Oxford Nanopore reads.                                         |
| Contig                              | A contiguous assembled sequence derived from overlapping reads.                                                                     |
| N50                                 | Minimum contig length such that 50% of the total assembly is in contigs of this length or longer. A common assembly quality metric. |
| GFA (Graphical Fragment Assembly)   | Standard format for representing assembly graphs, including contigs and their relationships.                                        |
| FASTA                               | Standard text format for nucleotide or protein sequences.                                                                           |
| FASTQ                               | Sequence format that includes per-base quality scores alongside the sequence.                                                       |
| Haplotype                           | One of two copies of each chromosome in a diploid organism. hifiasm can resolve both haplotypes separately.                         |
| Coverage / Depth                    | Average number of sequencing reads covering each position in the genome. Typically 30-50x for de novo assembly.                     |
| QUAST                               | Quality Assessment Tool for genome assemblies; computes metrics like N50, total length, and number of contigs.                      |
| BUSCO                               | Benchmarking Universal Single-Copy Orthologs; assesses genome completeness using conserved gene sets.                               |
| NanoPlot                            | Plotting and statistics tool for quality assessment of long-read sequencing data.                                                   |
| HTCondor submit file (`.sub`)       | Job description file used by HTCondor to submit tasks to the HTC system.                                                            |
| Apptainer                           | Container runtime (formerly Singularity) commonly used on HPC/HTC systems to run reproducible environments.                         |
| OSDF (Open Science Data Federation) | Federated data delivery infrastructure used for staging and retrieving large files across compute sites.                            |
| Pelican                             | Client tool for transferring data to and from OSDF origins and caches.                                                              |
| Staging (`/staging/`)               | CHTC shared file system for large files, mounted on execute points that advertise `HasCHTCStaging`.                                 |

## Compute Resources

Genome assembly with hifiasm is CPU- and memory-intensive but does not require GPUs. CHTC provides high-memory execute points suitable for genome assembly; see the resource table in [Submit Your Assembly Job](./04.5-Submit-Assembly.md) for guidelines by genome size. Key considerations:

* **Memory is the primary constraint.** hifiasm loads all read overlap information into memory, and insufficient memory is the most common cause of a failed assembly. Use `retry_request_memory` rather than over-requesting up front.
* **Thread scaling is limited.** hifiasm scales well to 16-20 threads; beyond that the speedup is small and the larger request waits longer for a slot.
* **Budget disk for input, intermediate, and output.** Intermediate files can be several times larger than the raw reads.
* **Expect queue time.** A request for 128 GB or more can wait hours for a slot, and very large assemblies that need 512 GB or more may wait a day or two. Use `condor_watch_q` to monitor, and plan accordingly.

If you would like to learn more about CHTC compute resources, visit the [CHTC Documentation Portal](https://chtc.cs.wisc.edu/uw-research-computing/).

## Software

In this tutorial you used an Apptainer container with hifiasm that CHTC distributes through OSDF, and the repository ships the recipe to build your own. The container can serve as a jumping-off point if you need to install additional software for your workflows.

Our recommendation for most users is to use Apptainer containers for deploying their software. For instructions on how to build an Apptainer container, see the guide [Using Apptainer/Singularity Containers](https://chtc.cs.wisc.edu/uw-research-computing/apptainer-htc). ## Data

Genome assembly involves large datasets, particularly for mammalian genomes, and understanding how data moves through the HTC system is essential for scaling assembly workflows. The key data components are:

* **Reads** (50-300+ GB per sample): stored in your `/staging` directory or on OSDF, and read in place by the job, as in this tutorial, or transferred with an `osdf:///` URL in `transfer_input_files` when the job runs outside CHTC.
* **Assembly outputs** (about 1-10 GB per assembly): GFA assembly graphs and FASTA contigs, packaged as `assembly_output.tar.gz` and remapped straight back to `/staging`.
* **Intermediate files** (variable, often larger than the reads): error-correction and overlap files written to the job's scratch disk and discarded with it.

:::{important} Keep large sequencing files out of `/home`
Read files are usually far too large for the CHTC `/home` directory, which has a limited quota. Store them in `/staging`, and reference them from your submit file by path (for jobs that read in place) or by `osdf:///` URL (for jobs that transfer them).
:::

For guides on how data movement works on the HTC system, see the [Data Staging and Transfer to Jobs](https://chtc.cs.wisc.edu/uw-research-computing/htc-job-file-transfer) guides.
