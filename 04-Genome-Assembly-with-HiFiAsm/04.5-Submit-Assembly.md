With the reads in `/staging`, you are ready to prepare and submit the assembly job.

## Prepare Your Assembly Job: Executable and Submit File

### The Executable File: `assembly.sh`

1. Change to your `tutorial-CHTC-Genome-Assembly/` directory:

   ```bash
   cd ~/tutorial-CHTC-Genome-Assembly/
   ```

2. Replace the contents of `scripts/assembly.sh` with the version below. The script runs hifiasm, converts the assembly graphs to FASTA, and packages the results:

   ```{code} bash
   :filename: scripts/assembly.sh
   :linenos:
   :emphasize-lines: 7,10
   #!/bin/bash
   # Run hifiasm on the EP and package the assembly
   # Usage: ./assembly.sh <output_prefix> <path_to_reads>
   set -euo pipefail

   OUTPUT_PREFIX=$1
   INPUT_READS=$2

   # Run hifiasm in ONT mode, reading the reads in place from /staging
   hifiasm -t"${PYTHON_CPU_COUNT}" --ont -o "${OUTPUT_PREFIX}.asm" "${INPUT_READS}"

   # Convert each primary-contig GFA to FASTA
   for gfa_file in *.p_ctg.gfa ; do
     fasta_file="${gfa_file%.gfa}.fa"
     awk '/^S/{print ">"$2; print $3}' "${gfa_file}" > "${fasta_file}"
   done

   # Package outputs
   tar czf assembly_output.tar.gz "${OUTPUT_PREFIX}".asm*
   ```

   The script takes two positional arguments:

   1. `<output_prefix>`: the name hifiasm prefixes every output file with (e.g. `Omalun-Tater`).
   2. `<path_to_reads>`: the full path of the reads in `/staging`.

   `PYTHON_CPU_COUNT` is set by HTCondor inside the job to the number of CPUs the job requested, so `-t` always matches `request_cpus`. The `awk` line keeps the `S` (segment) records of each GFA file, which are the contig sequences, and writes them as FASTA.

   :::{attention} How this script differs from the cloned one
   The script shipped in the repository hard-codes the reads path with a `<NetID>` placeholder, and after hifiasm finishes it runs `rm SRR22085263.fastq.gz`. That file never exists in the job's scratch directory, because the reads are read in place from `/staging`. Under `set -euo pipefail` the failed `rm` ends the script right there: the GFA files are never converted, `assembly_output.tar.gz` is never written, and HTCondor puts the job on hold for a missing output file, hours of assembly later. The version above takes the reads path as an argument and drops the `rm` line.
   :::

### The Submit File: `assembly.sub`

3. Open `assembly.sub` and edit it to match the version below. Replace the two `<netid>` placeholders with your NetID:

   ```{code} bash
   :filename: assembly.sub
   :linenos:
   :emphasize-lines: 2,5,13,19,22-25
   # Container for the hifiasm genome assembler, fetched from OSDF
   container_image         = osdf:///osg-public/containers/hifiasm_08APR2026_v1.sif

   executable              = scripts/assembly.sh
   arguments               = Omalun-Tater /staging/<netid>/tutorial-CHTC-Genome-Assembly/SRR22085263.fastq

   log                     = ./logs/assembly.log
   output                  = ./logs/assembly_$(Cluster)_$(Process).out
   error                   = ./logs/assembly_$(Cluster)_$(Process).err

   # Transfer the packaged assembly back to your /staging directory
   transfer_output_files   = assembly_output.tar.gz
   transfer_output_remaps  = "assembly_output.tar.gz = /staging/<netid>/tutorial-CHTC-Genome-Assembly/Assembly_Output/assembly_output.tar.gz"

   should_transfer_files   = YES
   when_to_transfer_output = ON_EXIT

   # The job reads the reads in place from /staging, so it must run on a CHTC machine that mounts it
   requirements            = (Target.HasCHTCStaging == true)

   # hifiasm for a ~2.4 Gb mammalian genome needs substantial resources
   request_cpus            = 16
   request_memory          = 128GB
   retry_request_memory    = 256GB
   request_disk            = 500GB

   queue 1
   ```

   Compared with the cloned file, this version passes the reads path in `arguments`, writes `output` and `error` to `logs/`, adds `retry_request_memory`, and drops a commented-out `transfer_input_files` line. The submit file:

   * Uses the prebuilt hifiasm container from OSDF.
   * Passes the output prefix and the reads path to `assembly.sh`.
   * Returns the assembly as a tarball and remaps it to `Assembly_Output/` in your `/staging` directory, where there is room for it.
   * Targets CHTC machines with `/staging` access, which rules out campus pools and the OSPool.
   * Requests 16 CPU cores, 128 GB of memory, and 500 GB of disk. If the job is held for exceeding 128 GB, `retry_request_memory` resubmits it with 256 GB automatically; see the CHTC guide on [requesting variable memory](https://chtc.cs.wisc.edu/uw-research-computing/variable-memory).

#### Choosing Appropriate Resources

Resource requirements for hifiasm depend primarily on **genome size** and **read coverage**:

| Genome size   | Coverage | Disk       | Memory     | CPUs  | Estimated runtime |
|---------------|----------|------------|------------|-------|-------------------|
| < 500 Mb      | 30-50x   | 100 GB     | 16-32 GB   | 8-16  | 1-3 hours         |
| 500 Mb - 1 Gb | 30-50x   | 150 GB     | 32-64 GB   | 16-32 | 2-6 hours         |
| 1 - 3 Gb      | 30-50x   | 300-500 GB | 64-128 GB  | 16    | 4-12 hours        |
| > 3 Gb        | 30-50x   | > 500 GB   | 128-256 GB | 20+   | 8-24+ hours       |

The Pallas's cat genome (~2.4 Gb) falls in the 1-3 Gb row, so this tutorial requests 128 GB of memory, 16 CPUs, and 500 GB of disk.

:::{note} These are guidelines
Actual requirements depend on genome complexity, repeat content, and coverage depth. Highly repetitive genomes and very high-coverage datasets may need 200 GB or more. Memory is the usual constraint, and running out of it is the most common cause of a failed assembly, which is what `retry_request_memory` is for. Beyond 16-20 threads, hifiasm gains little from more CPUs, and the larger request waits longer in the queue.
:::

## Submit and Monitor Your Assembly Job

4. Submit the job:

   ```bash
   condor_submit assembly.sub
   ```

5. Track its progress:

   ```bash
   condor_watch_q
   ```

   The job stays idle until an execute point with 16 free cores and 128 GB of free memory is available, which can take hours. Once it runs, hifiasm's progress messages go to the `.err` file in `logs/`; `tail logs/assembly_*.err` shows which stage it is in.

6. When the job finishes, the tarball is in `Assembly_Output/` in your `/staging` directory. Continue to [Understanding Your Assembly Output](./04.6-Assembly-Output.md).

:::{tip} Held jobs
If the job is held, `condor_q -hold` shows the reason. A memory overrun is handled by `retry_request_memory`. A disk overrun means the intermediate files outgrew `request_disk`; increase it with `condor_qedit <job_id> RequestDisk <new value in KB>` and `condor_release` the job, or edit the submit file and resubmit. For more details, see the HTCondor manual pages for [condor_q](https://htcondor.readthedocs.io/en/latest/man-pages/condor_q.html), [condor_qedit](https://htcondor.readthedocs.io/en/latest/man-pages/condor_qedit.html), and [condor_release](https://htcondor.readthedocs.io/en/latest/man-pages/condor_release.html), and the [CHTC guides](https://chtc.cs.wisc.edu/uw-research-computing/guides).
:::
