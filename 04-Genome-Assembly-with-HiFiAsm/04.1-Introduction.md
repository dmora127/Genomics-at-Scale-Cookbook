This tutorial guides you through a de novo genome assembly of Oxford Nanopore long reads with hifiasm on the CHTC high-throughput computing (HTC) system. You will learn how to:

* Understand the genome assembly workflow on CHTC, including how hifiasm maps to CPU, memory, and disk
* Stage a read set of hundreds of gigabytes in your `/staging` directory with Pelican and read it directly from a job
* Choose resource requests for a mammalian-sized genome and use CHTC's high-memory capacity
* Run hifiasm in a container that HTCondor fetches from the Open Science Data Federation (OSDF), and return the assembly to `/staging`
* Submit and monitor a job that runs for hours, and interpret hifiasm's output

Unlike the other recipes in this cookbook, which scale *out* by splitting a workload into hundreds of small jobs, this recipe scales *up*. A de novo assembly cannot be split: every read may overlap any other read, so the whole dataset has to be in one job's memory at once. The HTC skills here are different ones: sizing a single large request, moving data that is far too big to copy into a job, and keeping a job that runs for hours from failing on something avoidable.

## Understanding the Genome Assembly Workflow

Genome assembly reconstructs a genome from sequencing reads without a reference to map them to. Oxford Nanopore long reads, typically 10-100 kb, span most repeats, which is what makes chromosome-scale contigs possible from a single library.

[hifiasm](https://github.com/chhylp123/hifiasm) is a fast, haplotype-resolved de novo assembler. It was built for PacBio HiFi reads and, since version 0.21, also assembles Nanopore simplex reads with its `--ont` mode, which this tutorial uses. hifiasm works in four stages:

1. **Reads the raw reads** and corrects errors using all-vs-all read overlaps
2. **Builds an assembly graph** that captures the relationships between reads
3. **Resolves haplotypes** to produce separate assemblies for each parental copy of the genome
4. **Writes assembly graphs** in GFA format, which the job converts to FASTA for downstream analysis

The concepts in this tutorial apply to most other assemblers, such as Flye, Shasta, or Verkko. Only the container and the command line change.

### Key Characteristics of the Assembly Step

* **CPU-bound and memory-intensive**: hifiasm uses many threads and holds all read overlaps in memory. For a mammalian genome of about 2.4 Gb, expect to need 64-128 GB of memory and 16 CPU cores.
* **No GPU required**: the entire assembly pipeline runs on CPUs.
* **Data-intensive**: the reads for a mammalian genome run to hundreds of gigabytes. The reads in this tutorial are 318 GB uncompressed, so the job reads them in place from `/staging` instead of copying them.
* **Long-running**: a mammalian assembly takes 4-12 hours depending on coverage, genome complexity, and the machine it lands on.
* **Large scratch disk**: hifiasm writes error-corrected reads and overlap files that can be several times the size of the input. The job requests 500 GB of disk.

## One Job, Sized Right

Most of this recipe is about four lines of a submit file: `request_cpus`, `request_memory`, `request_disk`, and a `requirements` expression that keeps the job on a machine that can see `/staging`. Getting them right the first time matters more than usual, because a job that runs out of memory after eight hours has to start over. The tutorial therefore shows how to test the whole pipeline on a small subset of reads before committing to the full assembly, and how to use `retry_request_memory` so that HTCondor retries with more memory automatically instead of leaving the job on hold.
